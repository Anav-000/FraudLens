# FraudLens Architecture

## 1. System Overview

FraudLens is an independent verification platform designed to help everyday users evaluate suspicious communications (messages, job offers, payment demands, phishing alerts, URLs, and screenshots) before taking high-risk actions such as sending funds or disclosing confidential information.

The core philosophy of FraudLens is honesty, verifiable evidence provenance, and defensive user guidance:
- Distinguish clearly between deterministic checks, external reputation lookups, model-assisted interpretations, and unknowns.
- Avoid deceptive numerical risk scores or false "guaranteed-safe" verdicts.
- Maintain a clear separation of concerns between client presentation and server-side processing.

---

## 2. Frontend & Backend Responsibilities

### Frontend (React + TypeScript + Vite + Tailwind CSS)
- **Role**: Client interface, presentation, local input validation, and user interaction.
- **Responsibilities**:
  - Accept user-submitted text, files, and URLs without storing them across reloads in browser storage (`localStorage`, `sessionStorage`, or cookies).
  - Enforce client-side constraints (e.g. 10,000 character maximum limit, character count feedback, 2,048 character limit on URLs).
  - Communicate with the backend via centralized, timeout-bounded API clients using `AbortController`.
  - Accurately communicate backend availability and capability flags (never pretending features exist when they do not).
  - Support explanation language preference selection (English and Hindi).
  - Display untrusted URLs strictly as plain text with wrapping; never render submitted URLs as clickable HTML links (`<a>` tags).

### Backend (Python + FastAPI + Pydantic + Uvicorn)
- **Role**: Validated API gateway, credential boundary, and core analysis engine.
- **Responsibilities**:
  - Keep AI provider credentials strictly server-side; secrets are never sent to the client, included in client bundles, or logged.
  - Enforce schema contracts and reject unexpected fields (`extra="forbid"`).
  - Sanitize validation error responses to ensure raw user inputs and sensitive substrings are never reflected in error payloads.
  - Enforce CORS policies restricted strictly to configured local frontend origins.
  - Provide structured status endpoints (`/api/v1/health`, `/api/v1/capabilities`), analysis endpoints (`/api/v1/analyze/text`), extraction endpoints (`/api/v1/extract/*`), and local URL inspection (`/api/v1/inspect/url`).

## 3. Evidence Provenance & Quality Principles

FraudLens categorizes findings into explicit provenance types to preserve transparency:

1. **Deterministic Checks & Local Inspection**:
   - Rule-based inspections (e.g., mismatched display names vs email headers, urgency triggers, known high-risk UPI handles, suspicious payment schemes).
   - Local URL structure parsing (destination hostname extraction, PSL registrable domain derivation, userinfo detection, IP literals, punycode, non-default ports).
2. **External Reputation Findings (Planned)**:
   - Lookups against independent reputation databases (e.g., domain age, URL threat feeds).
   - *Crucial rule*: A clean reputation lookup never proves a URL is safe; it only indicates the absence of known malicious history. Local structural inspection is NOT external reputation checking.
3. **Model Interpretations**:
   - Structured reasoning generated by an AI provider regarding psychological manipulation, impersonation tactics, and contextual inconsistencies.
   - Provider citations must be tied strictly to verified content and never hallucinated.
4. **Unknowns & Missing Data**:
   - Areas where the input lacks sufficient detail to verify claims (e.g., unverifiable company references, newly registered domains, lack of counterparty verifiable records).

### Text Grounding & Evidence Validation (Implemented in Phase 2B)
- **Verbatim Substring Grounding**: Every warning sign returned by the model must include an `evidence_quote` that is strictly verified to exist as an exact substring of the user-submitted text (`quote in submitted_text`). Fabricated quotes or hallucinated text citations are rejected with an explicit `INVALID_RESPONSE` error. Substring checks verify quote presence only, not the factual accuracy of the model's interpretation.
- **Cross-Field Invariants**: An assessment of `warning_signs_found` requires at least one verified warning sign. Assessments of `no_clear_warning_signs` and `insufficient_information` strictly enforce an empty warning signs array.
- **Prompt Injection Defense**: Untrusted text is strictly encapsulated in `<UNTRUSTED_MESSAGE>` tags. Defensive system instructions mandate that embedded instructions within the message body be treated as passive evidence rather than executable commands. Tools and external search grounding are completely disabled (`tools=None`).
- **Plain-Text URLs**: URLs appearing inside evidence quotes are rendered strictly as unlinked plain text to prevent accidental phishing navigation by users.

## 4. Privacy & Data Lifecycle

- **Phase 2B Text Analysis Workflow**:
  - Strictly in-memory and transient.
  - Zero database persistence and zero server-side logging of submitted text or raw provider outputs.
  - Responses enforce `Cache-Control: no-store` to prevent intermediary or browser caching of analyzed text.
  - Explicit privacy notice displayed directly to the user.
- **Phase 4A URL Inspection Workflow**:
  - Strictly offline and local.
  - Submitted URLs are never logged or persisted on the server (they may contain sensitive tokens or userinfo).
  - All success (HTTP 200) and validation failure (HTTP 422) responses return `Cache-Control: no-store`.
- **Free Tier Policy Boundaries**:
  - Operating on Google AI Studio Free Tier requires using fictional development data only.
  - Requesting `store=False` in `GenerateContentConfig` opts out of developer-owned interaction logging in Google AI Studio project history where supported; it does not provide zero data retention or override Google's safety/abuse monitoring or free-tier service terms.
- **Future Case Storage Architecture (Opt-In)**:
  - When case persistence is introduced in later phases, it will be strictly opt-in.
  - Proposed storage: **SQLite** for metadata and case relationships, plus **private local file storage** for uploaded screenshots/documents.
  - *Requirement*: Local files must be stored outside public web roots and protected by access controls.
  - Full user controls will be provided to delete saved cases and associated evidence at any time.

## 5. Provider Adapter Architecture

To prevent tight coupling with any single AI provider or SDK:
- An isolated adapter module (`backend/app/services/gemini.py`) implements the integration using the official `google-genai` SDK.
- Configurable selected model (`AI_MODEL=gemini-3.5-flash-lite`).
- Strict 30-second timeout and zero automatic retries (`attempts=1`).
- Zero model fallback: Missing or unavailable models produce explicit `MODEL_UNAVAILABLE` errors rather than silent switches.
- Missing configuration or provider connection failures are surfaced explicitly as structured status errors rather than unhandled 500 exceptions or fabricated fallbacks.
- Never silently substitute fixture results for live analysis in production.

## 6. Local File Extraction & Review Architecture (Phases 3A & 3B)

To support analyzing evidence received in screenshots or documents without compromising privacy or security:

### A. Local Backend Processing & Privacy Boundary
- **Zero Cloud Transmission of Files**: Screenshots and PDF documents are processed **100% locally on the backend server**. Raw files, image pixels, and document binaries are **never** transmitted to Google Gemini, cloud OCR APIs, or external services.
- **Human-in-the-Loop Review**: Extracted text is returned to the user in an editable review interface. Downstream Gemini analysis is triggered only after the user explicitly reviews, confirms, transfers, and clicks "Analyze Message".
- **Evidence Provenance Boundary**: Downstream text analysis evaluates the *submitted reviewed text only*. Analysis findings concern textual patterns, not document authenticity, digital signatures, visual tampering, sender identity, or URL reputation.

### B. Screenshot OCR Engine (Phase 3A)
- **Engine**: Local Tesseract OCR CLI invocation paired with Pillow image validation.
- **Constraints**: Single static PNG or JPEG image ($\le 5$ MiB, $\le 12$ megapixels). Multi-frame/animated images and decompression bombs are rejected.
- **Dual Event Loop Compatibility**: Uses `asyncio.to_thread` with synchronous runner fallback on Windows `SelectorEventLoop` (Uvicorn `--reload` mode) and Proactor loop. Bounded concurrency (`asyncio.Semaphore(3)`) and 20.0s timeout with process kill and reaping.

### C. PDF Document Text Extraction (Phase 3B)
- **Library Selection**: **`pypdf`** (`pypdf>=5.0.0,<6.0.0`, version 5.9.0).
  - *Rationale*: Permissive BSD-3-Clause license, maintained pure-Python library, zero native C-compilation dependencies, compatible across Windows and Linux.
  - *Security Properties*: Does not execute embedded PDF JavaScript, does not open embedded file attachments, does not follow external links/URIs, and does not render visual raster graphics.
- **Separately Terminable Worker Process**:
  - Untrusted PDF parsing runs in an isolated Python subprocess (`app.services.pdf_worker`) rather than a worker thread. This ensures that memory consumption, infinite object loops, or malicious compression bombs can be forcibly terminated via OS-level process kill (`proc.kill()` on Windows via `TerminateProcess`) and reaped cleanly without lingering threads.
- **Enforceable Memory Limit (Windows Job Objects)**:
  - *Mechanism*: On the supported Windows environment, `pdf_worker.py` applies an OS-enforced virtual memory limit via Windows Job Objects (`JOBOBJECT_EXTENDED_LIMIT_INFORMATION` setting both `JOB_OBJECT_LIMIT_PROCESS_MEMORY` and `JOB_OBJECT_LIMIT_JOB_MEMORY`) strictly *before* opening or parsing untrusted PDF bytes.
  - *Threshold*: 256 MiB per worker process.
  - *Failure Behavior*: When memory allocation reaches the 256 MiB ceiling, the OS rejects virtual allocation calls with `ERROR_COMMITMENT_LIMIT`, causing Python's memory allocator to raise `MemoryError`. This is caught and mapped to HTTP 500 / `DOCUMENT_EXTRACTION_FAILED` with an actionable error message. If the process terminates abnormally without writing output, `DocumentService` handles missing output safely as `DOCUMENT_EXTRACTION_FAILED`.
  - *Platform Support*: Windows Job Objects provide the enforced memory ceiling on the primary Windows deployment target (`sys.platform == "win32"`). On POSIX environments, `resource.setrlimit(resource.RLIMIT_AS, ...)` is called on a best-effort basis; universal memory enforcement across unverified OSs is not claimed.
- **Bounded I/O & Worker Result Byte Limits**:
  - `stdout` and `stderr` are discarded using `subprocess.DEVNULL`, preventing child process pipe buffers from accumulating unbounded output in the parent process.
  - Worker output JSON is strictly bounded to $\le 1$ MiB (`MAX_WORKER_RESULT_BYTES = 1024 * 1024`). The worker verifies byte size before writing to disk, and the parent `DocumentService` checks file size before opening or parsing JSON.
- **Combined Concurrency Clarification**:
  - PDF document extraction concurrency is bounded by `_document_semaphore = asyncio.Semaphore(3)`.
  - Concurrency for screenshot OCR is bounded by `_ocr_semaphore = asyncio.Semaphore(3)`.
  - These two semaphores operate independently: the backend permits up to 3 active OCR workers plus 3 active PDF worker processes simultaneously (up to 6 concurrent extraction worker subprocesses total across both modalities), rather than a single shared semaphore of 3.
- **Page & Text Limits**:
  - Maximum document length: 10 pages (`MAX_DOCUMENT_PAGES = 10`). Oversized documents are rejected with HTTP 422 `PAGE_LIMIT_EXCEEDED` (never silently truncated).
  - Maximum extracted text: 10,000 characters (`MAX_EXTRACTED_CHARACTERS = 10_000`). Text exceeding this is rejected with HTTP 422 `TEXT_TOO_LONG`.
  - Incomplete extraction warning: If only some pages contain extractable text, empty page numbers are identified and an incomplete-extraction warning is displayed.

## 7. Local URL Structure Inspection Architecture (Phase 4A)

To help users understand where suspicious links lead without opening them or leaking browsing intent:

### A. Core Distinction: Local Inspection vs. External Reputation
- **Available: Local URL Structure Inspection**:
  - Purely offline structural decomposition of submitted URL strings.
  - Reveals the actual destination hostname, port, userinfo credentials, IP address literal classification, IDNA punycode, and Public Suffix List (PSL) registrable domain.
- **Planned: External Reputation Checks**:
  - Live querying of threat intelligence services (Google Safe Browsing, VirusTotal, WHOIS domain age registries) is **planned for future milestones** and **not implemented in this phase**.
- **Fundamental Limit**: Structural analysis alone **never** proves a URL is safe or malicious. A clean domain structure does not guarantee safety, and a non-default port or direct IP address is not inherently fraudulent. Neither provides proof of sender identity.

### B. Strict No-Network Boundary
- A URL parser must **never** become a URL fetcher.
- The inspection pipeline enforces a strict zero-network boundary:
  - Zero DNS resolution (`socket.getaddrinfo` is never called).
  - Zero HTTP/HTTPS requests or socket connections (`socket.connect` is never called).
  - Zero asset downloads, page fetches, favicon queries, or link previews.
  - Zero calls to WHOIS registries or external threat APIs.
  - Zero calls to Google Gemini during URL inspection.
- The existing text-analysis response property `external_checks_performed` strictly remains `false`.

### C. Parsing Libraries & Offline PSL Resolution
- **Standard Library Parsing**: Uses Python's standard `urllib.parse.urlsplit` and `ipaddress` libraries. Monolithic regular expressions are not used for URL parsing.
- **Pre-parsing Validation**: Control characters (ASCII < 32 or 127) and whitespace are validated and rejected before `urlsplit` to prevent silent stripping or normalization.
- **IDNA 2008 & Punycode**: Uses the `idna` package to encode and decode internationalized domain labels, verifying label length ($\le 63$ octets) and total domain length ($\le 253$ octets). Displays both Unicode representation and ASCII punycode (`xn--...`).
- **Offline Public Suffix List (`tldextract`)**:
  - Uses `tldextract` strictly configured for offline operation (`cache_dir=None`, `suffix_list_urls=()`). Runtime PSL downloads are completely disabled.
  - Includes RFC 2606 / RFC 6761 reserved testing TLDs (`extra_suffixes=['invalid', 'test', 'example', 'localhost']`) to reliably extract registrable domains without falling back to two-label approximations.
  - Arbitrary two-label splitting (e.g. treating `co.uk` or `gov.in` as registrable domains) is strictly avoided.

### D. Deterministic Observations & Calibrated Wording
- `unencrypted_http`: Informational. Unencrypted transit; notes that HTTP alone does not prove fraud.
- `userinfo_present`: Caution. Credentials before `@` in netloc do not represent the destination domain; highlights actual destination host.
- `ip_literal_host`: Caution. Destination is a direct IP address. Scope noted (private, loopback, public). Notes an IP address is not inherently malicious.
- `special_use_address`: Informational. Explains special-use/private/loopback scope without asserting network reachability.
- `punycode_hostname`: Informational. Explains IDN legitimacy alongside lookalike caveat.
- `non_default_port`: Informational. Identifies port without labeling it malicious.
- `deep_subdomain_hierarchy`: Caution. Threshold $\ge 3$ subdomain levels. Explains deep subdomain risk objectively.

### E. Frontend Presentation
- Plain-text URL rendering with CSS `break-all`; submitted URLs are **never rendered as clickable HTML links (`<a>` tags)**.
- Destination hostname is prominently styled in a highlighted card so users immediately see where the link actually points.
- Modifying the URL after inspection marks results as stale.
- Requests use `AbortController` to cancel in-flight inspections on edit, reset, or re-submit, preventing late responses from overwriting user edits.
